SECTION 1: CORE FLOW STABILIZATION

These are the most important tasks. Do these before any extra visual upgrades.

--------------------------------------------------
1.1 DEPOSIT / ADD FUNDS FLOW
--------------------------------------------------

Current problems:
- Deposit flow has thrown runtime errors before
- Some payment methods appear but are not active
- Crypto deposit flow needs to be 100% secure
- User should never be able to credit themselves manually
- Deposit status needs to be clear

Required behavior:

When user clicks Scalps balance or Add Funds:
1. Open Add Funds modal/drawer.
2. Load available payment methods from backend.
3. Only show payment methods that are actually enabled and working.
4. Show loading state while methods are loading.
5. If methods fail to load, show:
   “Deposits are temporarily unavailable. Please try again soon.”

Crypto deposit flow:

Step 1:
User selects crypto method:
- Bitcoin
- Ethereum
- Solana
- USDC if supported

Step 2:
User enters deposit amount.

Validate:
- amount is above minimum
- amount is below maximum
- user is authenticated
- user email is verified if required
- user is eligible to deposit

If validation fails:
- Do not continue
- Show clean message

Examples:
- “Please verify your email before adding funds.”
- “Minimum deposit is X Scalps.”
- “Deposits are not available in your region.”

Step 3:
User clicks Generate Deposit Address.

Frontend:
- button enters loading state
- text changes to “Generating address...”
- disable repeated clicks

Backend:
- creates pending deposit record
- requests deposit address from provider
- returns deposit ID, address, network, amount, expiration time

Frontend displays:
- QR code
- wallet address
- copy button
- network name
- amount to send
- warning:
  “Only send this asset on the selected network. Sending the wrong asset may result in loss.”

Important:
Remove or disable any button that says:
“I’ve sent funds”
if it credits balance.

Replace it with:
“Track Deposit”

Track Deposit button should:
- refresh deposit status
- never update balance by itself

Deposit statuses:
- pending
- waiting_for_payment
- confirming
- confirmed
- failed
- expired

UI status display:
Pending:
“Deposit created. Send funds to the address below.”

Waiting:
“Waiting for payment detection.”

Confirming:
“Payment detected. Waiting for blockchain confirmation.”

Confirmed:
“Deposit confirmed. Funds added.”

Failed:
“Deposit failed. No funds were added.”

Expired:
“This deposit expired. Please create a new one.”

Balance update rule:
Balance ONLY updates after backend receives verified payment confirmation from provider/webhook.

Never:
- update balance when address is generated
- update balance when user clicks Track Deposit
- update balance from frontend state only
- trust client payment status

Required backend protections:
- verify webhook signature
- store webhook event ID
- prevent duplicate webhook processing
- update balance inside database transaction
- create transaction record
- link transaction to deposit ID

Required UI polish:
- balance count-up animation only after confirmed backend update
- blue/green glow on confirmed deposit
- success message:
  “Deposit confirmed. Your balance is ready.”
- show transaction in history immediately after confirmation

--------------------------------------------------
1.3 MATCH JOIN FLOW
--------------------------------------------------

Current problems:
- Users see errors after they already click join
- “Cannot join your own match” appears incorrectly
- Device restrictions are caught too late
- Some matches show 0 Scalps confusingly

Required match join flow:

When user views match cards, frontend should already know:
- match ID
- game
- stake
- pot
- players joined
- device restriction
- status
- creator type
- whether current user can join

Each match card must run eligibility display logic.

Before user clicks:
If device mismatch:
- button disabled
- text: “Mobile Only” or “Desktop Only”
- badge visible on card
- tooltip:
  “This match can only be played on mobile.”

If insufficient balance:
- button text: “Add Funds”
- clicking opens Add Funds
- do not open wager modal

If match full:
- button disabled
- text: “Full”

If match expired:
- hide or mark expired
- do not allow join

If match is available:
- button text: “Join Match”

When user clicks Join Match:
Step 1:
Frontend calls backend eligibility check:
GET /matches/:id/eligibility

Backend checks:
- user authenticated
- match exists
- match status is waiting/open
- match not full
- user not already in match
- user has enough balance
- user device allowed
- user is not improperly joining own private match

Important own-match logic:
Only block if:
- match.creatorId === user.id
AND
- match.type === private/custom/player_created
AND
- match.status === waiting

Do not block:
- bot matches
- free practice matches
- system generated matches
- queue matches
- tournament matches

Step 2:
If eligible:
Open wager confirmation modal.

Wager modal must show:
- game
- opponent or waiting status
- required stake
- total pot
- platform fee/rake
- winner receives
- user balance after joining
- confirm button

If stake is 0:
Show clearly:
“Free Practice Match”
Do not show:
Required Wager: 0 Scalps
Total Pot: 0 Scalps
unless styled as practice/free mode.

Step 3:
User confirms.
Backend joins match inside database transaction.

Backend:
- re-checks eligibility
- deducts stake if required
- creates transaction record
- adds user to match
- updates match status if full
- returns updated match

Frontend:
- shows success state
- transitions to match lobby/game

Error handling:
Do not show raw 400/403.
Map errors:

DEVICE_NOT_SUPPORTED:
“This match is not available on your device.”

INSUFFICIENT_FUNDS:
“You need X more Scalps to join.”

MATCH_FULL:
“This match just filled up.”

OWN_MATCH:
“You already created this private match.”

MATCH_EXPIRED:
“This match expired.”

--------------------------------------------------
1.5 BALANCE SYSTEM
--------------------------------------------------

Balance is critical.

Rules:
- frontend never decides balance
- backend is source of truth
- every balance change creates transaction record
- balance display must always match transaction history

Balance change sources:
- confirmed deposit
- match stake deduction
- match win payout
- tournament entry
- tournament payout
- shop purchase
- withdrawal

Every balance mutation must:
- happen server-side
- use database transaction
- log previous balance
- log new balance
- create transaction row
- be idempotent if from external webhook

Frontend:
Listen for balance_update websocket.
When received:
- animate from old balance to new balance
- show floating + or - amount
- refresh transaction history silently
